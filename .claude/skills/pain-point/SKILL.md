# 痛点の記録（SDK 側）

mobile-mr では「デモを作って苦しいところを貯める」のが目的だった。このリポジトリでは **「SDK を作って使ってみて苦しいところ」** を貯める。段階3 の差し替え（ドッグフーディング）で見つかる API の使いにくさが、段階4（フレームワーク化）の要求仕様になる。記録はコードと同じ成果物。

## 記録先

このリポジトリの `docs/PAIN_POINTS.md` の**末尾**に追記する（時系列の古い → 新しい）。ファイルが無ければ見出しを付けて作成する。
**mobile-mr 側の `../mobile-mr/docs/PAIN_POINTS.md` には書き込まない**（mobile-mr 側は触らない）。mobile-mr の痛点への「解消 / 仕様として明記 / 対象外」の付け替えは `docs/<module>.md` の表で行う（new-module スキル手順 1）。

## フォーマット（mobile-mr と同じ。見出しの 2 つ目だけ「モジュール / 差し替え先デモ」）

```markdown
## [YYYY-MM-DD] <モジュール / 差し替え先デモ>: <一言タイトル>

- **何が苦しかったか**: 具体的に。API 名・引数・エラーメッセージを含める
- **どう対処したか**: 回避策・妥協した点。mobile-mr 側に回避策を書いたならそれも。未解決なら「未解決」
- **SDK の API をどう変えるか（案）**: この痛みを SDK 側で吸収する案。段階4 送りなら「段階4」。思いつかなければ「未定」
- **関連**: SDK のコード（`src/core/session.ts:42` 形式）、差し替え先（`../mobile-mr/demos/01-stereo-box/main.ts:12`）、元になった mobile-mr の痛点（`PAIN_POINTS.md` の日付とタイトル）、issue / PR の URL
```

例:

```markdown
## [2026-09-20] core / 01-stereo-box: Session の開始に渡すフックが 5 つあり、01 は 2 つしか使わないのに全部書かされる

- **何が苦しかったか**: `createSession({ onSensor, onCamera, onFullscreen, onWake, onError })` を 01 で呼ぶと、カメラを使わない 01 でも `onCamera` を渡さないと型が通らない
- **どう対処したか**: 01 側で空関数を渡した（mobile-mr 側に SDK 都合のノイズが入った）
- **SDK の API をどう変えるか（案）**: フックを optional にし、使う機能（camera / fullscreen）を宣言する形に。または段階を分けた builder
- **関連**: `src/core/session.ts:30`、`../mobile-mr/demos/01-stereo-box/main.ts:18`、mobile-mr PAIN_POINTS 2026-08-21「開始フローのボイラープレートが 4 本目」
```

## 記録すべきもの

- **段階3 で見つかった API の使いにくさ**（← 最重要。引数が多い・順序が不明・型が合わない・mobile-mr 側に回避策を書きたくなった・同じ組み合わせを毎回書く）
- **参照実装を写していて分かった暗黙の前提**（座標系・単位・既定値の理由が不明、`fov=auto` のようにデモ間で意味がずれていた値）
- **mobile-mr の痛点のうち、SDK では解消できなかったもの**（「仕様として明記」に落とした理由）
- **実機とフェイク入力で挙動が違った箇所**（フェイクの仮定が間違っていた。pc-check の「未検証（仮定）」が外れたとき）
- **iOS / Android / PC の差で SDK 側に分岐が増えた箇所**
- **テストしにくかった箇所**（ブラウザ API に絡んで Node で回せず、ヘッドレスでも再現できない）

## 注意

- 「解決したから記録しなくていい」ではない。**解決できた痛みこそ API 変更の候補**なので必ず残す
- 些細に見えても、2 回目に遭遇したら必ず記録する（繰り返しは共通化 = 段階4 のシグナル）
- 段階4 の設計を先取りして書かない。「案」は 1〜2 行にとどめ、実装しない
